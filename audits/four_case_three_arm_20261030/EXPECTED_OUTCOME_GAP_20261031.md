# Gap between the research hypothesis and observed outcomes

The research hypothesis is that the isolated Agents can reliably complete each task and that the shared desktop introduces additional failures. The current samples do **not** establish that pattern. These are fixed-version observations, not estimates of population success rates. A task failure and a separately observed focus incident are reported separately.

| Case | Valid formal episodes | Observed outcome and limit |
|---|---|---|
| 3 Build-and-Verify v1.0.6 | One per condition | Isolated, Shared and Shared+Lock all failed jointly. In Isolated, A spent its budget searching several incorrect spellings and did not save a repair. In Shared, B's `Ctrl+L` landed in A's Gedit after the foreground window changed; B recovered, while A also made a separate incorrect code edit. The lock arm had negligible contention. [Evidence](../case3_three_arm_20261030/TRIAD1_RESULT.md) |
| 6 Spreadsheet Handoff v1.1 | One per condition | Isolated and Shared passed; Shared+Lock failed because A left a source-evidence cell blank while B waited. All three had zero overlapping GUI input intervals. One sample per condition does not establish stability or a lock effect. [Evidence](../three_lite_cases_20261029/CASE6_V1P1_TRIAD1_20261030.md) |
| 7 Workspace Assembly v1.2 | Two per condition | All six final artifacts passed the Oracle. Shared and Shared+Lock each had one directly observed `Ctrl+O` in A's foreground Gedit; B recovered. A's messages included the tag, and B also saw A's open document, so the information source cannot be determined from these trajectories. The simple Shared input lock was validated against real concurrent input calls, but the formal Case 3, 6 and 7 trajectories had little or no lock contention. It cannot preserve the foreground application between an Agent's screenshot and its next action. Case 7 shows a misrouted shortcut even while that input call held the lock. The samples do not establish its effect on success rate.

## Candidate directions and current status

Case 6 v1.2 and Case 7 v2 have since been implemented as separate candidates. Their offline tests do not establish model performance. Case 6's current real-Guest controls are in progress; Case 7 has not yet received its new real-Guest controls. The historical observations above remain unchanged. Case 5 is paused and Case 3 remains assigned to the collaborator.

* **Case 3:** Put the defective short line in the initial editor viewport, open the same publishable revision-zero page in both topologies, and let B refresh after A's saved revision and verify one filter. This preserves A's repair → saved revision → B's real browser check while reducing search and path-entry burden. Verify revision delivery and browser cache behavior with GUI positive and negative controls before any model comparison. Case 3 is also assigned to a collaborator; coordinate any future change in a separate version and branch.
* **Case 6:** Make the output cells and units prominent; consider a public generic formula that calculates cost from B's still-unknown order quantity. A must still derive net demand, and B must derive box-rounded quantity. Existing evidence shows message/revision use and subsequent edits, but does not establish that B independently read A's file in GUI. A requirement for file reading would need a common public entry point and separate behavioral evidence.
* **Case 7:** In a new version, consider A's message carrying only availability and revision, while B reads the task value from the delivered file using equivalent access in both topologies. A short useful pre-handoff B action could preserve natural concurrency. A file-open trace and screenshot can support a process observation, but cannot establish the model's internal reasoning. New fixtures and evaluation must be frozen and validated in both topologies before comparison.

None of these directions changes the existing tasks, scores or observations. Future versions should first demonstrate basic Isolated feasibility, then use preregistered paired repeats with the same inputs, prompts, model, budget and scorer. A stronger observation-to-action lock, if studied, is a separate arm with its own waiting and concurrency costs; it is not a substitute for the no-lock Shared baseline.
