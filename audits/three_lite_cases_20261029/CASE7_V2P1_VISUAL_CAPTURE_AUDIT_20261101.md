# Case 7 v2.1 first control: peer-view screenshot mismatch

The first v2.1 Shared scripted positive, `wa-lite-v2p1-control-positive-shared-20261101T092423Z-2498655`, ran from `b8fc08a877e55b85ce04177beade7e1f880daa3f`. It exited `0/PASS` after 931 s: A, B and joint artifact Oracle passed; A/B reopen had identical bytes; the bridge reported no error; single-Guest reset was clean; the QEMU and dual-filesystem resource audit was valid. It is retained locally as a genuine positive control with a **screenshot-timing anomaly**. It must not be mixed into any later six-control series from a different source commit.

The saved GUI trace establishes that B invoked Writer Open, entered the published `views/B/inspection_note-r000001.txt` path and, after the picker remained open, clicked its visible green Open button. The next X11 sample reported a new active Writer window ID `41952341` titled `inspection_note-r000001.txt (read-only) - LibreOffice Writer`; `wmctrl` listed that window at the expected geometry. The peer view mode was `444` and its recovered bytes matched A's revision SHA. The trace therefore supports an attempted GUI opening and a real read-only window.

The visual frame lags behind the X11 title. [B-010](evidence/case7_v2p1_first_control_B_stale_report.png) after the button action and `screenshots/control_B_peer_view.png` about nine seconds later are byte-identical (SHA-256 `e6457d747f60ca1792e8e4c70c12a62f6b3132ab046b5ffd82320d51577c9db5`) and both still show the old `handoff_report.odt`. Crucially, [B-011](evidence/case7_v2p1_first_control_B_delayed_note.png) captured **after** a `Ctrl+W` action, when X11 said the active window was back to `handoff_report.odt`, shows the read-only note's title and body. The preceding [Open-dialog frame](evidence/case7_v2p1_first_control_B_picker.png) shows the exact peer-view path. Taken together, the GUI action, window chronology and delayed visible note frame support a real GUI read in this control; the dedicated `control_B_peer_view.png` is mistimed and must not be cited alone as the visual proof. The copied frames retain source paths and SHA in their [manifest](evidence/case7_v2p1_first_control_visual_manifest.json).

The follow-up code change adds a **control-only, read-only observation gate** in the v2.1 path. It saves a before frame, then samples X11 active titles and screenshots within 45 s. It requires the expected read-only title both before and after each capture, a changed center title-bar dark-text shape relative to the before frame, and two consecutive stable candidate crops. The change threshold is a fraction of crop area rather than a fixed pixel count. The raw RGB crop changed by 1308 pixels between two old-report frames solely because focus styling changed; the dark-text mask changed by only 121 pixels (0.26% of the crop), versus about 1870 pixels (4%) for a previously retained visible note frame. These values are diagnostic, not a file-identity classifier. Every sampled PNG, timestamp, WM title and crop-change count is retained. If no candidate appears, the control fails closed; it sends no additional GUI input, reads no inspection tag and changes no task, prompt or Oracle. A changed crop is only a **candidate**: a human still must inspect the selected full screenshot for the visible file title or body. Shared and Isolated v2.1 controls use this same branch. The old v2 case path is unchanged.

Offline validation: targeted tests cover stale-screen, wrong-title, focus-recolor and delayed-frame cases. Python compilation and `git diff --check` were run. No further Guest or model run was started after the first control. Any resumed six-control series must use one new source commit across all six; retain this initial attempt separately.
