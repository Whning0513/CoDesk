# Case 7 Workspace Assembly Lite v1.0.2: two preregistered three-arm repeats

**Status:** six formal model episodes completed on real OSWorld Ubuntu Guests on 2026-10-31. All six used frozen source commit `b09f8c5aba01fcffa67ec5abbdd8888572b6afce`, `gpt-6-astra`, the same public files, role prompts, 25 desktop calls per role, 1200 seconds of active model time, wait/wake lifecycle, and independent artifact Oracle. The fixed order was Isolated → Shared → Shared+Lock → Shared+Lock → Shared → Isolated, as [preregistered](CASE7_V1P2_THREE_ARM_PROTOCOL.md). Every planned arm was run once; no formal sample was removed or replaced.

The **artifact Oracle passed jointly in all six**. This is not a six-for-six verification of the stricter role process. In both Isolated episodes, timestamped GUI Open actions and screenshots support B independently reading A's delivered note in its own Guest. In all four Shared episodes, B saw the note in A's already-open shared desktop window, then edited Writer without independently opening the delivered file as the v1.0.2 B prompt requests. The read-only automatic process auditor reports `v1p2_full_process_verified=false` for all six because its strict window-title test misses A's visually verified Text Editor opening and the Isolated B read-only Writer title omits the full path. Those cases require the separately documented screenshot review below. The artifact Oracle and original audit outputs were not changed.

## Handoff and focus evidence

1. **Isolated arms 1 and 6:** A moved the original 89-byte `inspection_note.txt` from `incoming` into `outputs/agent_A`, opened it in Text Editor, published revision 1 and messaged B. The [A screenshot from arm 1](evidence/case7_v1p2_isolated1_A_delivered_open.png) and [A screenshot from arm 6](evidence/case7_v1p2_isolated2_A_delivered_open.png) show the delivered directory, filename and `RIVER-27`. B was suspended until A's revision/message became visible. B then typed the full delivered path into its own Writer GUI Open dialog, submitted it, and saw a read-only note containing `RIVER-27` in [arm 1](evidence/case7_v1p2_isolated1_B_readonly_note.png) and [arm 6](evidence/case7_v1p2_isolated2_B_readonly_note.png). It returned to its own report, edited the target line and saved. The bridge recorded A revision 1 with SHA `4b18022a28c6ed4af5a476469c9f796514fab91711645c53bcba576fbe4b3595` in B Guest; final A/B revisions and reopen SHA matched. This supports the complete A→B GUI process after manual review.
2. **Shared arm 2:** After A opened the delivered note and sent the handoff, B woke to [A's Text Editor in the foreground](evidence/case7_v1p2_shared1_B_A_gedit_foreground.png). Its `Ctrl+O` action had `window_before=inspection_note.txt ... - gedit`, so it opened a dialog in A's application rather than its own Writer. B closed the dialog, navigated back to Writer and saved a correct report. This is direct focus misrouting with visible recovery. The artifact passed; B did not independently GUI-open the note.
3. **Shared+Lock arm 3:** B woke to A's gedit, cycled through Files/gedit, eventually created an untitled Writer window, reopened the report, and spent 24 desktop calls before saving a correct report. All 31 executed A/B GUI input actions acquired the lock, with total wait about 0.001 s. The lock did not restore B's Writer foreground. There was no evidence of two simultaneous input calls in the unlocked trajectory either.
4. **Shared+Lock arm 4:** B again pressed `Ctrl+O` with A's gedit foreground, then closed the wrong dialog and recovered Writer. The [wake screenshot](evidence/case7_v1p2_shared_lock2_B_A_gedit_foreground.png) and action windows support the misrouting. All 18 executed A/B input actions acquired the lock, with negligible acquisition wait. B saved a correct artifact without independently opening the note.
5. **Shared arm 5:** B saw A's gedit but clicked the Writer dock icon before editing. This avoided the earlier wrong-window `Ctrl+O`; its artifact passed in 8 desktop calls. It still used the shared displayed note rather than independently opening the delivered file.

The automatic [handoff auditor](audit_case7_handoff.py) has two relevant limits. Its `behavioral_handoff_verified=true` in Shared means B's action timestamps saw an already-open delivered-path window; it does **not** prove B itself opened the file. Conversely, its `v1p2_full_process_verified=false` and `manual_review_required=true` in Isolated are conservative false negatives against the screenshots: A's Text Editor title lacks the full folder path, and B's read-only Writer title has only the basename. Its candidate screenshot path is one image later than the displayed read-only frame in these runs; the visual proof is `shots/008.png` for arm 1 and `shots/010.png` for arm 6. The source audit results remain preserved, and this report labels the visual conclusion as **manual review**, not an Oracle pass.

## What the lock ablation says

The simple `flock` serialized individual mouse/keyboard tool calls in both Shared+Lock runs, with 100% of executed input calls marked locked. Lock acquisition wait was practically zero because the Agents' GUI action intervals did not overlap; their model requests did overlap. It did not keep each Agent's own application in the foreground across calls, and B's wrong-window `Ctrl+O` recurred in arm 4. Both Shared and both Shared+Lock artifacts passed, so this two-repeat cohort provides **no joint-success improvement from the lock**. It does show that input-call serialization alone does not solve persistent shared desktop focus state or the prompt-level requirement that B independently open the delivered revision. The large first lock cost is one model recovery path, not evidence that locking generally raises token use. A future action lock should not be claimed as an adequate replacement for isolated desktops without broader paired trials.

## Evidence and scope

Each local run directory retains full Actor traces, per-step action JSON and screenshots, collaboration messages, workspace revisions/transfers, final artifacts, independent `oracle.json`, reopen/reset evidence and QEMU samples. The selected screenshots above are copied with SHA and source run paths in [their manifest](evidence/case7_v1p2_selected_screenshots_manifest.json), and all six B Writer files plus the identical A note are copied with SHA in the [artifact manifest](evidence/case7_v1p2_final_artifacts/manifest.json). The complete raw runs remain local because of size. The formal run source sidecars all equal `b09f8c5`; no frozen source file changed during the six arms. The provider credential was loaded only into the coordinator environment and is absent from the committed evidence. Results are descriptive for one Case and two repeats per condition; they do not estimate a stable population success rate or a causal lock effect.

**Case design consequence:** v1.0.2 reliably permits correct saved artifacts and A→B information use. The stricter B independent GUI-open rule is naturally bypassed on Shared because A's opened file is visible on the common desktop. If that rule is essential to the benchmark's process endpoint, future versions should make its scoring explicit and independently observable for both topologies; any change to the task or Oracle requires a new version and fresh controls. Do not retroactively relabel these six episodes.
