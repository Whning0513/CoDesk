# Case 5 dedicated Docker recovery, 2026-10-31

The `mar-lite-v1-triad1-isolated-20261031T062318Z` attempt failed before model execution: B's Blender setup lost the Guest screenshot endpoint, and the dedicated rootless Docker socket then refused connections. The runner recorded `INVALID_INFRA_OR_RUNNER_ERROR`; its two cleanup calls could not reach Docker. The run and its `failure.json`, GUI/setup logs and provenance remain under the original run ID. It is not a model outcome.

The dedicated daemon was restarted using its existing `.codesk-docker` data and execution roots. Its API reported Docker 29.0.2, the expected data root and zero containers. Provenance tied the remaining orphan shims to the two run-owned container IDs `01e86325df12be824c4ff09dc5bfa2fd0cda3fd9a9f894f558a0a2037b4aa571` and `e40fd98967b001bd8fd8577c808c966eb5d543fceb79f232ce4c68faf3f32a74`; their QEMU children had already exited. Each shim was checked for its exact container ID, dedicated containerd socket, parent PID 1 and no children before SIGTERM. Both exited. The machine-readable [cleanup record](case5-062318-orphan-shim-cleanup.json) preserves the target identities and checks. No system Docker daemon or unrelated container was stopped.

A labeled disposable shell container using the existing `oscombo/qemu-runtime:local` image exited 0 and printed `codesk-docker-health-ok`. Afterwards the dedicated daemon showed zero containers and no QEMU process; `/data3` had 22,633,193,472 bytes free. This verifies basic Docker create/start/remove only; it is not a Guest GUI smoke test.

The old daemon log ends abruptly after the second Guest was created, without a recorded graceful shutdown or conclusive crash reason. It records `failed to add inotify watch ... memory.events: no space left on device` for both run-owned containers. The user systemd journal also reports failed control and memory cgroup watches for B. Read-only inspection found the per-user `max_user_watches` limit at 65,536, with 65,536 watches accounted for at sampling time; a VS Code Server process owned by the same user held 65,231. A bounded temporary probe could allocate only two of 64 requested watches before `ENOSPC`, and released them afterwards. The sysctl is not writable by this user. This is evidence of inotify exhaustion and impaired cgroup event monitoring, not proof that it caused the daemon exit. The other process was not changed. The user slice and root cgroup OOM counters showed zero events; kernel dmesg was not accessible to this user.
