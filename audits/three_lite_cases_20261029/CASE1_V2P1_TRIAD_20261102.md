# Case 1 Data-to-Deck Lite v2.1: one three-arm comparison

## Scope and prior results

The case is `CDD-LITE-002`, version `2.0.1` (Lite v2.1). A verifies the West Q3–Q2 financial change and saves its Calc analysis; B uses A's saved handoff and message to revise a single Impress conclusion. The v2.1 Oracle separately accepts equivalent unit expressions. Original tasks, old v2.0 Oracle, and historical episodes were not overwritten.

The 2026-10-27 Isolated model episode failed because B ended before A's handoff. The lifecycle-repaired 2026-10-28 formal Isolated artifact Oracle passed, while Shared's frozen Oracle failed on an equivalent unit phrase; an explicitly post-hoc equivalent-expression audit passed both. A real Guest Isolated wake diagnostic also passed, but used a B-only diagnostic instruction. Furthermore, the historical Isolated formal transcript contains one failed attempt to call `x.read_mcp_resource`, outside the later strict Actor tool contract. These historical observations are not counted as this new three-arm cohort.

This cohort uses source `b45717f7e04934e5c63fd27e66a5c46db75da5b2`, `gpt-6-astra` medium, identical prompts, deterministic public fixtures, per-role 25 GUI-call / 1,200 active-second budget, the same scoring, saved-file bridge and suspend/wake behavior. Shared+Lock adds only the existing per-input GUI lock; screenshots and model requests remain concurrent. Shared has one desktop; Isolated has two. No task answer, Gold, Oracle or provider credential is given to an Actor.

Before the three arms, Shared and Isolated positive controls passed, and the Shared deliberately wrong-value negative was rejected for the expected reason; real GUI, artifacts, independent Oracle, bridge audit, reopen and reset evidence were retained. The Shared positive was recorded on `0575340`; the subsequent source changes add only post-run bridge/artifact audit and provenance, and its original evidence was independently rechecked. The other controls and the Pilot used `b45717f`. The sole Isolated Pilot passed with A/B 10/10 GUI calls; B suspended 332.786 s, then read A's handoff message, edited and saved. Its strict transport, tool-boundary, bridge and resource checks passed. It is not a formal observation.

The three-arm sequence and configuration were frozen before the first formal arm in local `runs/case1-cohort-20261102/freeze.json` (SHA-256 `22054ad975d72a2f6f0c68f43893e3e37fb1390e8c31550d60ee4cd6323f609c`). Each arm ran exactly once in the planned order; no sample was discarded or selected for score.

All three are complete **valid** task observations: their independent artifact Oracle passed both roles, every SSE event reached `response.completed` (27/27, 34/34 and 30/30, respectively), both Actor tool-boundary checks were clean, final bridge history had no transient error, each scored artifact reopened with matching bytes, Guest reset completed cleanly, and dual-filesystem/Guest resource checks passed. The sampled RSS figures are from `resource_samples.jsonl`, not the older metrics utility's zero-valued QEMU aggregate. The isolated setup/total and RSS include two Guests; time differences are not a pure topology effect.

In all three arms B voluntarily suspended with no new B output before A's handoff; the coordinator resumed the same Actor after A's saved revision and message arrived without sending the answer itself. A's actual message did include Q2/Q3 values, the signed change, source-cell range and saved revision, as the role instructions request. B's real `read_messages` result included this body and B also called `list_saved_artifacts`; B then edited and saved Impress. The messages contained no attachments, and there were no `read_attachment` calls. We did **not** observe B opening A's ODS in the GUI during the Actor phase; evaluator-side GUI reopen is not evidence that B did so. Thus the evidence establishes a message-carried numerical handoff and a saved revision, not GUI reading of A's workbook.

The older `audits/lite_v2_20261027/audit_handoff.py` returns `strict_behavioral_handoff=false` for both Shared arms because it only recognizes an inter-Guest `transfer_verified` event or the original `revision_saved.delivered` field. On the current shared bridge the corresponding same-desktop `revision_committed` event carries the matching revision and SHA; no inter-Guest copy is expected. The new separate `data_to_deck_lite_v2_1.audit_handoff` checks the committed archive hash, chronology, actual B message read and subsequent GUI edit/save, and records this narrower finding without changing the old audit or Oracle.

The first actual B GUI input followed A's last by approximately 79 s in Isolated, 87 s in Shared and 77 s in Shared+Lock. Accordingly, Shared has no observed simultaneous input or demonstrated cross-Agent focus misrouting in this sample. In the lock arm all 17 executed input calls had the mutex enabled, but total lock wait was only approximately 0.000398 s. Because the two actors' GUI input did not overlap even without the lock, this cohort does not test whether a lock would resolve active contention, nor does it show meaningful lock overhead. The desired hypothesis of Isolated PASS / Shared FAIL was **not observed** here; one triad cannot establish stable success rates.
