# Public artifact lookup timeout during Case 7 whitelist repeat

The first scheduled whitelist Shared episode, `wa-lite-v1p1-whitelist-pair1-shared-20261030T095158Z`, entered a real Guest with two concurrent model Actors. B suspended after its first desktop call while awaiting A. A performed real File Manager actions, but the episode ended before scoring with `INVALID_INFRA_OR_RUNNER_ERROR`: the coordinator's `/artifacts` request timed out after 15 seconds. The collaboration server later logged a broken pipe while trying to answer that request. No Oracle result exists, so this run is not a model FAIL or a valid topology score.

The cause is the bridge's `snapshot()` acquiring the same lock as `publish()` and the periodic saved-file scan. Those paths hold the lock during slow TCG Guest file reads and peer transfers. Public revision lookup is read-only and has a 15-second client timeout; it can therefore fail even though the Guest and model are progressing. This lock is for version/ownership bookkeeping, not GUI input.

The repair reads the bridge's atomically replaced `current.json` manifest for public snapshots without acquiring the Guest I/O lock. A lookup sees the last fully committed revision until the next publish completes. It cannot see a half-written transfer as delivered. The explicit publish request now permits up to 120 seconds for its two Guest reads and optional Isolated transfer; short message and list lookups keep their normal timeout. A regression test holds the bridge I/O lock while another thread obtains a public snapshot promptly. This is the same shared bridge and client behavior in Shared and Isolated; no model prompt, task, Oracle, or mouse/keyboard scheduling changes.

The immediately following Isolated diagnostic was already launched by the fixed-order script before this fault was diagnosed. The outer script was stopped after that launch to avoid starting the remaining two episodes on a known-broken harness. The Isolated child and run-owned sampler were allowed to complete and clean their own resources; their outcome will be reported separately. A new uniquely identified pair series will use the repaired coordinator. The old attempts remain in their run directories and are not silently replaced.
