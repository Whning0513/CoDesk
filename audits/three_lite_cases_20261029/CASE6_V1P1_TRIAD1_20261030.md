# Case 6 Lite v1.1: first frozen three-arm model comparison

Run cohort: `case6-v1p1-triad1-20261030T225247Z`; executed 2026-10-30/31 UTC. The manifest is `case6-v1p1-triad1-20261030T225247Z.tsv`. Raw run roots, screenshots, actor rollouts, workspace revisions, messages, GUI actions, model relay events, Oracle results and postscore evidence remain under `runs/sh-lite-v1p1-triad1-{isolated,shared,sharedlock}-20261030T225247Z/` in the independent Case 6 worktree. Those run roots are intentionally ignored by Git and were not rewritten. The three arms ran once in the preregistered order, with no success-based repeats.

All arms used the same `CDD-SH-LITE-001` v1.1.0 Fixture, A/B prompts, `gpt-6-astra` medium, 25 desktop calls per role, 1200 seconds active role time, `--handoff-lifecycle --yield-wait-lifecycle`, request-level Actor MCP allowlist and independent Oracle. A and B model processes started concurrently. Only the third arm used `--gui-input-lock`. A Guest action is real Calc GUI input on an OSWorld Ubuntu QEMU/TCG Guest. Isolated used two Guests with revision/message transfer and read-only peer copies; Shared and Shared+Lock used one Guest.

## Failure attribution and practical interpretation

Isolated A saved `H3=73` and source `I3=B3:G3`; B saved 80 order units and USD 2240. Shared produced the same correct values and source. In Shared, B deliberately changed focus from `forecast.ods` to `order_plan.ods` after the handoff; its input actions were logged in the expected window. No cross-Agent input misrouting or focus stealing was observed in this triad.

In Shared+Lock, A's real GUI trace shows an extra `Ctrl+O` Open dialog, a return to `forecast.ods`, repeated clicks in Calc's name box, and repeated entry of `B3:G3` there. The preserved A screenshot `actor_runs/A/A/shots/021.png` shows `H3=73`, `I3` empty and the name box containing `B3:G3` after A saved. Independent Oracle accepted A's numeric net need but rejected `evidence_covers_sales_and_inventory`. B had been suspended throughout A's GUI actions, so this was A's own GUI navigation/error recovery failure, not a cross-Agent focus conflict. B later saved correct local `E3=80`, `F3=2240`, and source `forecast.ods`; its individual Oracle is FAIL only because `matches_saved_forecast` requires a valid saved A analysis. B's local order quantity, cost, budget and source checks passed. The lock arm's trace chronology was valid, while `correct_joint_handoff=false` because the saved A artifact was incomplete.

The first triad establishes that both baseline topologies can complete v1.1 with a real handoff, and that the simple input lock was actually enabled in the third arm. It does **not** establish a topology success-rate difference or a lock benefit/harm: one sample per arm, no input contention, different stochastic model paths, and the lock-arm error happened while B waited. The protocol's second reverse-order triad remains preregistered but was not started in this work round.
