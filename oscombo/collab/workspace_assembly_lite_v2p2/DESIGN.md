# Workspace Assembly Lite v2.2 candidate

This is a new case version. It does not change v2.1's Fixture, Gold, Oracle, runs or scores. The valid v2.1 Isolated round-one run showed B opening A's read-only revision in Writer, then entering an incorrect long tag and joining its audience and attachment text. Those two failures were ordinary GUI transcription/paragraph editing, not a workspace bridge failure. This version reduces those operations without supplying the answer.

A still moves the only incoming `inspection_note.txt` with Files, publishes its saved bytes through the same immutable revision bridge, and sends only availability/revision metadata. B can prepare the Writer report while A works, saves its audience value before handoff, then independently opens the published read-only revision in a real GUI and reads its inspection code. The code appears only in A's public source note; it is not in B's prompt, report template, case brief or A's message. A and B remain concurrent. Shared still has one unlocked desktop and natural focus competition; Isolated still uses two desktops and the same bridge. A simple per-input GUI lock remains an optional third arm, identical task semantics.

Both topologies install the same public source, report and brief. In Shared the file is reachable in the single filesystem; in Isolated it is reachable in each Guest's initial workspace. B's initial Writer window, Prompt and brief are code-free, but a B Agent could navigate to the original note in either topology. The role instruction forbids that route and the behavioral audit flags original/input-path access. The comparison therefore does not rely on a topology-specific information barrier: valid collaboration requires A's byte-preserving move and publication plus B's actual GUI read of the immutable delivered revision, confirmed separately from the artifact Oracle. This is a behavioral benchmark, not role-level filesystem security.

The new source uses a seed-derived three-digit code from digits 2–9, rather than an alphanumeric tag that contains visually confusable letters and digits. The independent Writer ODT has five separate paragraphs from the start: title, audience clue, `Source: inspection_note.txt`, `Audience:`, and `Inspection code:`. B fills only ` operations` and later ` 682` (example code), not the filename or an entire sentence; the code field is already a separate paragraph, so B does not insert an Enter to create it. The setup places B's caret after `Audience:` with the same GUI actions in both topologies. After the GUI read, Ctrl+End reaches the code field. The scripted critical path still contains 15 physical GUI inputs (A 5, B prework 2, B open 4, B finish 4); the amount of text and paragraph manipulation are lower. This is a design estimate, not a model tool cap or real Guest result.

The independent Oracle checks A's byte-preserving move and absence from incoming; B's real ODT, preserved title/audience-clue/source line, separate audience and code paragraphs, audience derived from the draft, and code exactly matching A's delivered bytes. It additionally reports whether B matches the original public source. A wrong A artifact can therefore make B's local answer correct relative to the delivered file while joint success fails. Missing delivery leaves B's handoff score unknown when all its other checks pass. GUI reading, timing, message leakage and immutable-revision evidence are assessed separately by the behavioral audit and screenshots; artifact correctness alone never proves the handoff process.

Gold/Oracle live only on the scoring side. The candidate has offline positive and negative controls; no v2.2 Guest or model result is claimed in this document. Real GUI controls must verify Writer caret placement, saved prework and code field, peer-view screenshot, reopen/reset and both topologies before a Pilot or formal freeze.
