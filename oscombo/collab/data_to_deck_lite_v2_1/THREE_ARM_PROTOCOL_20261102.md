# Case 1 v2.1: three-arm prospective validation

The prior v2.0 lifecycle formal pair is retained unchanged. Its Shared frozen Oracle failed only on an equivalent unit phrase; its Isolated Oracle passed but B attempted one additional `x.read_mcp_resource` tool, which failed. These historical results are not a new request-allowlisted three-arm cohort. A previous real Isolated wait/wake diagnostic passed, but used a diagnostic B instruction. The v2.1 real Shared/Isolated positive and Shared wrong-value negative controls have also passed on the earlier source; no historical records are overwritten.

Before model collection, run Shared and Isolated scripted positives and the Shared wrong-value negative on the new source; verify actual Guest screenshots, outputs, bridge, independent Oracle, reopen and reset. Then run one isolated concurrent Pilot with 18 GUI calls and 900 active seconds per role; keep its outcome regardless of score. The Pilot uses the same task and tool policy; its result is not a formal arm.

After review, run one Isolated, one Shared, then one Shared+Lock episode, in that order. All roles use gpt-6-astra medium, identical public fixture and role instruction, 25 GUI calls and 1,200 active seconds, request-level desktop/collaboration allowlist, the same file bridge and Oracle, the same yield/wake lifecycle, one real Guest per desktop and 8 vCPU/8 GiB per Guest. Only Shared+Lock enables the existing per-input mutex. GUI screenshots remain unlocked. This is a coordination ablation, and no Shared-specific obstacle or answer is introduced.

Run IDs are unique; retain all outcomes. Record every provider transport event, including incomplete streams, and actual tool calls. A non-200, missing `response.completed`, tool-boundary violation, bridge fault, missing reopen/reset, incomplete resource observation or disk below 15 GiB is infrastructure review rather than a task failure. Do not replay a partial stream, GUI action or pick model-success runs. Abort further arms on invalid infrastructure until the fault is assessed. Gold and Oracle remain scoring-side only. Each role works in its original Actor environment; the credential is available only to the coordinator/relay.

Independent reports must distinguish final Oracle and actual handoff (messages, revisions and GUI read); inspect screenshots and timing before attributing a failure to focus competition. Report token, setup/model/postscore times, wait/wake, active overlap, input overlap, lock acquisition/wait and sampled resources. A single triad does not estimate a stable success rate or prove causation.
