# Case 6 v1.2 three-arm study: preregistration draft

Status: **candidate, not frozen**. Commit and freeze only after the shared immutable revision bridge and lifecycle change have been reviewed and integrated, all offline checks pass, actual Shared and Isolated Guest controls pass, screenshots are visually reviewed, and the bounded model Pilot completes with an inspectable chain. No model or Guest episode is authorized by this document until the coordinator allocates a resource window and confirms the dedicated Docker and host readiness.

## Hypotheses and fairness

The study asks whether the independent desktop baseline can reliably complete this task, whether a shared desktop creates additional focus or application-state errors, and whether serializing one GUI input call changes outcomes or costs. None is assumed true. Use the same `CDD-SH-LITE-002` v1.2 Fixture, A/B prompts, publicly available metadata and immutable B view, model `gpt-6-astra` medium, tools, scorer and budgets in all arms. Gold and Oracle stay on the scoring side. A may report ready, but should not communicate the numeric result; preserve all messages unchanged and separately flag any result disclosure. B prepares the generic E3×C3 formula through Calc before viewing the revision and obtains the result from a real GUI view; no model-time agent action is scripted by the harness.

Shared is one Guest with the normal shared foreground, keyboard and pointer; no input lock. Isolated uses two Guests and equal saved revision/message access. Shared+Lock is the same Shared setup plus the pre-existing run-scoped mutex around each GUI input call; screenshots and reasoning remain outside the lock. No input scheduling favors one role. Model processes start at a barrier, not necessarily at the same desktop action.

## Gates and controls

1. Offline tests cover fresh blank public results, source protection, correct A and B numeric outputs, valid equivalent cost formulas, wrong formula, case count, cost or cap, wrong A with correct B relative to the delivered value, malformed/short ODS and host I/O errors. Round-trip public and Gold ODS through a local LibreOffice profile. These are offline tests only.
2. Real Guest scripted controls run once each in the fixed order: positive Shared, positive Isolated, wrong-units Shared, wrong-units Isolated. B prepares F3 in the GUI before A's saved result; A calculates, saves and sends a nonnumeric ready message; B opens revision zero and the current revision in Calc through the same public view paths. Verify the old view remains byte-identical and read-only, is recognized as stale, and displays a blank result; verify the latest revision has the published SHA, mode 444, a different immutable filename and visible saved H3 in a real screenshot. B then enters the intended units, saves, and receives independent Oracle positive or expected wrong-unit negative. Both topology conditions require complete artifact collection, postscore GUI reopen, clean run-owned resets and recorded resource profile. Before accepting controls, separately review screenshots and record their SHA, revision, path, visible result and reviewer in `peer_view_visual_review.json` and `stale_view_visual_review.json`; `verify_controls` checks this record against each exact image. A window title/hash alone is not sufficient.
3. Run one Isolated concurrent model Pilot, 18 GUI calls and 900 active seconds per role, with the same version, tools and lifecycle. The extra diagnostic headroom covers the revision-opening and return path while remaining below the full budget. Inspect actual A/B requests, message contents, saved revision/mirror, B prework and GUI view screenshots, A/B files and scorer, reopen/reset and resource metrics. Record the SHA and visual review of both the formula-preparation screenshot and the exact delivered-revision screenshot; `verify_pilot` checks these records and message review. The pilot is diagnostic and never counted in full samples. A valid task failure is retained; missing evidence to establish the model's ability to obtain/read the view is a gate failure, not a reason to selectively tune one topology. Fix a proven infrastructure issue symmetrically and repeat the relevant controls before freezing.

The opt-in mirror requires same-path `views/B/forecast-rNNNNNN.ods`, verified SHA and 444 mode before `delivered=true`, with old revisions retained. Persistent view/transfer/ownership faults, malformed bridge logs, unresolved save retries or pending revision states mark infrastructure review required even if final sync later succeeds. Ordinary save-in-progress retries subsequently confirmed committed are recorded separately. Failed starts and score results stay under their original run IDs.

## Frozen model cohort

After the gates, freeze one source commit, fixture hashes, public prompts, model/endpoint, tool allowlist, Oracle, lifecycle and budgets. Use 25 GUI calls and 1200 **active** seconds per role, with voluntary wait time excluded equally in all arms. Fixed per-Guest QEMU allocation is 8 vCPU and 8 GiB. Capture settings and actual QEMU command line; sample per-Guest CPU/RSS and host CPU, available memory, swap, free disk, I/O counters and pressure. Stop before an arm if dedicated Docker health is uncertain, another Guest is active, or free space is below 15 GiB. If Guest, bridge, model transport or postscore evidence is invalid, preserve the attempt and symmetrically repair/revalidate before a replacement; never replace a valid task FAIL.

Collect at least three complete rounds in this fixed order, one episode per arm per round:

1. Isolated → Shared → Shared+Lock.
2. Shared+Lock → Shared → Isolated.
3. Isolated → Shared+Lock → Shared.

Record each run's A, B local and B global checks, joint Oracle and separate behavior evidence. B local success is evaluated against the saved A result; a wrong A value must not automatically erase B's local calculation, but joint success still requires the true A result. GUI viewing is judged from delivered revision/hash, B's metadata and action chronology, matching screenshot and visual review, never from a self-reported hash alone. Flag B's visible pre-handoff work and whether A disclosed the answer. Count setup, Actor execution, GUI action and screenshot durations, provider request/token use, suspended waiting, effective A/B active overlap, GUI input overlap and lock wait/hold separately. Inspect each focus change or misroute and recovery, preserving all raw records.

Report each arm's success count and denominator, a binomial confidence interval, event counts and the complete run IDs. Three samples per arm give wide intervals and cannot establish stable success or a causal advantage. Avoid a lock success claim without observed contention and without sufficient repeated outcomes. Isolated uses two Guests; compare aggregate resource use and avoid attributing setup differences solely to desktop topology.
